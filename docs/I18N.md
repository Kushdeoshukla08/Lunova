# Internationalisation

Lunova ships in **English only** today. This document describes the architecture
that makes adding a language a *data* change, not a code change — and the
regional behaviour (timezones, distance units, date formats) that is already
live for every user regardless of language.

## What is already international

Even with one UI language, these adapt to the viewer:

| Concern        | Source of truth                                                                 |
| -------------- | ------------------------------------------------------------------------------- |
| Timezone       | signed-in user's `profile.timezone` → `lunova_tz` cookie → `UTC`               |
| Distance units | viewer region (`profile.country`), else **metric** — never guessed from language |
| Date / time    | `Intl.DateTimeFormat` with the resolved locale + timezone                       |
| Numbers        | `Intl.NumberFormat` with the resolved locale                                    |

Dates are never rendered in the server's local zone. `UTC` is the explicit
fallback until the client reports its zone (once, via `TimeZoneSync`) or the
user saves a profile timezone.

## Modules

```
src/lib/i18n/
  config.ts        LOCALES, DEFAULT_LOCALE, isLocale, unitSystemFor, labels
  locale.ts        (server-only) resolveLocale / resolveTimeZone / getI18n
  format.ts        pure Intl-based formatters — locale + tz aware, no context read
  actions.ts       setLocaleAction (cookie), setTimeZoneAction (cookie)
  messages/
    en.ts          the base catalog — a plain nested object of strings
    index.ts       getDictionary(locale), t(dict, key, vars)
src/components/i18n/timezone-sync.tsx   client → server tz handshake
```

`src/lib/format.ts` is now a thin re-export of `src/lib/i18n/format.ts` so
existing `@/lib/format` imports keep working; new call sites should import the
context-aware functions and pass a `FormatContext`.

## Locale resolution

`resolveLocale()` (server-only), in priority order:

1. `lunova_locale` cookie — an explicit choice in **Settings → Language & region**
2. `Accept-Language` header — first entry whose base tag is a shipped locale
3. `DEFAULT_LOCALE` (`en`)

Only members of `LOCALES` are ever returned, so an unknown `Accept-Language`
can never produce a half-translated page.

## Timezone resolution

`resolveTimeZone(preferred?)`:

1. `preferred` — pass `profile.timezone` when you have the user loaded
2. `lunova_tz` cookie — set once by `<TimeZoneSync>` from
   `Intl.DateTimeFormat().resolvedOptions().timeZone`
3. `"UTC"`

All candidates are validated against `Intl` before use.

## Formatting

`format.ts` functions take an optional second arg:

```ts
formatRelative(date, ctx?)      // "now" · "5m" · "3h" · "Tue" · "12 Mar"
formatTime(date, ctx?)          // "2:30 PM" — in ctx.timeZone
formatDayHeading(date, ctx?)    // "Today" / "Yesterday" / "Friday, 28 August"
formatDate(date, ctx?)          // full calendar date, locale order
formatNumber(n, ctx?)
formatDistance(km, ctx & { precision? })   // coarse, privacy-preserving
```

`ctx` is `{ locale, timeZone, units }`. With no `ctx` they fall back to English
+ runtime timezone + metric, so they're safe in any component. Server
Components get `ctx` from `getI18n()` / `getFormatContext()`; Client Components
receive it as a prop (see `MessageThread`, `AppShell`).

`describeDistance` in `src/lib/compatibility/geo.ts` takes an optional
`units` arg and stays metric by default; the Discovery feed passes the viewer's
resolved unit system through `getDiscoveryFeed(userId, { units })`.

## Messages

`en.ts` is the complete catalog. Any future locale is a `DeepPartial` of it and
is `deepMerge`d over English at read time — a missing key renders in English,
never as a raw key.

```ts
const { dict } = await getI18n();
dict.nav.discover;               // typed access
t(dict, "settings.language.title");          // dot-path + {var} interpolation
```

Components are **not** being bulk-migrated to `t()`. The dictionary currently
covers the app-shell navigation and the Language settings screen — enough to
prove the pattern. New user-facing strings should go through the dictionary;
existing copy is migrated opportunistically.

## Adding a language

1. `src/lib/i18n/messages/<locale>.ts` — `export const <locale>: DeepPartial<Messages> = { … }`
2. Register it in `messages/index.ts` `CATALOGS` and add the tag to `LOCALES`
   and `LOCALE_LABELS` in `config.ts`.
3. If the locale genuinely implies a region, add it to
   `LOCALE_DEFAULT_COUNTRY` / `IMPERIAL_COUNTRIES` in `config.ts`.
4. The Settings picker, `<html lang>`, `Accept-Language` negotiation and
   fallback all pick it up with no further changes.

## Not done here (deliberately)

- **No URL-segment locales** (`/en/…`). Cookie + header negotiation only; revisit
  if SEO for translated marketing pages ever matters.
- **No translation of the ~150 existing component strings.** Architecture first.
- **No RTL styling pass.** Add with the first RTL locale.
- **International phone numbers** already handled at input: E.164 validation in
  `src/lib/verification/actions.ts` (`^\+[1-9]\d{6,14}$`).
